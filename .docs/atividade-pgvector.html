Atividade — busca semântica com pgvector

Nos passos 04 a 08 da aula, a busca semântica de livros (UC24) guardou os vetores num índice HNSW do Redis. Nesta atividade, os vetores mudam de casa e vão para o próprio PostgreSQL, com a extensão pgvector. O embedder, o Gemini, o limiar, a rota e a página continuam os mesmos. Mudam o lugar onde os vetores ficam guardados e a consulta que encontra os vizinhos.

Este enunciado dá bastante dica. Ele não traz a solução, mas mostra cada peça do pgvector com exemplos de código em domínios de brinquedo: uma tabela brinquedo com vetores de 3 dimensões e uma tabela filmes. 01

O que fazer

Leve o armazenamento dos vetores da busca semântica (UC24) do Redis para o PostgreSQL com pgvector, sem mudar o contrato da API: GET /api/busca-semantica/livros?q= continua respondendo o mesmo JSON, com a mesma distancia, e a página /livros/semantica funciona sem nenhuma alteração.

Dentro do escopo

  • O serviço db do compose passa a ter a extensão pgvector.
  • A aplicação cria a extensão vector sozinha, de forma idempotente, tanto no banco da aula quanto no de testes.
  • Uma tabela de vetores dos livros, do módulo Acervo, com uma coluna vector(N) (N vem do embedder) e um índice HNSW com distância cosseno.
  • Cadastrar, editar e excluir livro e renomear autor mantêm essa tabela em dia, depois do COMMIT, sem derrubar a escrita se o Gemini falhar.
  • O seed e a subida do servidor reconciliam: livros sem vetor, ou com texto desatualizado, ganham vetor novo.
  • Trocar de embedder (outro modelo ou outra dimensão) refaz a tabela, como o Redis refazia o índice.
  • A busca acha os vizinhos com o operador <=> no Postgres, aplica o mesmo limiar maxDistance e responde o mesmo JSON, com 400 e 503 como antes.
  • O Redis deixa de guardar o índice dos livros: a busca semântica funciona com o Redis parado.
  • Testes automatizados para tudo isso.

Fora do escopo

  • O frontend não muda.
  • O embedder (Embedder.ts, gemini.ts, hashEmbedder.ts, embedder.ts) não muda.
  • O cache da busca de autores continua no Redis. O Redis não sai do projeto, só deixa de cuidar dos vetores.
  • O limiar continua 0,38 para o Gemini e 0,6 para o hash. O passo 02 explica por quê.
  • Busca híbrida (palavra-chave + vetor) fica para a discussão do passo 08.

Por que o limiar não muda

No Redis, DISTANCE_METRIC COSINE devolve 1 − cos(θ). No pgvector, o operador <=> devolve exatamente a mesma coisa: 1 − cos(θ). Para os mesmos dois vetores, os dois bancos dão o mesmo número. O maxDistance de 0,38 que a turma calibrou no passo 08 continua valendo, e a página continua mostrando a similaridade como 1 − distancia.

03

pgvector em 15 minutos

Antes de mexer no projeto, brinque com o pgvector num banco descartável, com vetores de 3 dimensões, pequenos o bastante para fazer a conta de cabeça. Tudo o que você vai precisar no projeto aparece aqui.

1. Troque a imagem do Postgres

O postgres:18 oficial não traz o pgvector. A imagem pgvector/pgvector:pg18 é o mesmo Postgres 18, com a extensão já compilada. Em infra/compose.yaml, no serviço db, troque image: postgres:18 por image: pgvector/pgvector:pg18. Depois recrie o contêiner:

terminalPowerShell
docker compose -f infra/compose.yaml up -d db
E os meus dados? Ficam. A versão do Postgres é a mesma (18) e o volume pgdata é o mesmo: o contêiner novo abre os arquivos do antigo. A extensão só existe num banco depois que alguém roda CREATE EXTENSION nele.

2. Um banco de brinquedo

terminalPowerShell
docker compose -f infra/compose.yaml exec db createdb -U biblioteca brincadeira
docker compose -f infra/compose.yaml exec db psql -U biblioteca -d brincadeira

Agora você está no psql. Ative a extensão e confira:

sqlpsql
CREATE EXTENSION IF NOT EXISTS vector;
\dx

Na lista de extensões aparece a linha vector, com a versão (0.8.1 ou mais nova) e a descrição vector data type and ivfflat and hnsw access methods.

3. Uma tabela com vetores

sqlpsql
CREATE TABLE brinquedo (
  id   INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  nome TEXT NOT NULL,
  v    vector(3) NOT NULL          -- 3 dimensões; no projeto, N vem do embedder
);

-- o vetor entra como texto entre colchetes
INSERT INTO brinquedo (nome, v) VALUES
  ('gato',      '[0.9, 0.1, 0.0]'),
  ('leão',      '[0.8, 0.2, 0.1]'),
  ('geladeira', '[0.0, 0.1, 0.9]');

Pense na 1ª dimensão como "é um felino" e na 3ª como "é um eletrodoméstico". O Gemini faz algo parecido, só que com 768 dimensões que ninguém sabe nomear.

4. Os vizinhos mais próximos

A consulta é o vetor [1, 0, 0], "algo bem felino". Quem está mais perto?

sqlpsql
SELECT nome, round((v <=> '[1, 0, 0]')::numeric, 4) AS distancia
FROM brinquedo
ORDER BY v <=> '[1, 0, 0]'
LIMIT 2;
saída esperada
 nome | distancia
------+-----------
 gato |    0.0061
 leão |    0.0369

Repare no par ORDER BY … LIMIT: é a forma do KNN no SQL, e é ela que o índice HNSW sabe acelerar. O round é só para a saída ficar legível. No projeto você quer a distância inteira.

OperadorMedeClasse de operadores do índice
<=>distância cosseno, 1 − cos(θ): a da aulavector_cosine_ops
<->distância euclidiana (L2)vector_l2_ops
<#>produto interno, com sinal trocadovector_ip_ops

5. A dimensão é verificada

sqlpsql
INSERT INTO brinquedo (nome, v) VALUES ('erro', '[1, 2]');
SELECT nome, vector_dims(v) FROM brinquedo LIMIT 1;
saída esperada
ERROR:  expected 3 dimensions, not 2
 nome | vector_dims
------+-------------
 gato |           3

Compare com o Redis, que aceitava o HSET e simplesmente deixava o livro fora do índice. Por isso o bookIndex.ts precisava do HSTRLEN. Aqui o erro aparece na hora.

6. O índice HNSW

sqlpsql
CREATE INDEX ON brinquedo USING hnsw (v vector_cosine_ops);

-- com 3 linhas, o planejador prefere ler a tabela inteira (Seq Scan);
-- desligar o Seq Scan só nesta sessão mostra que o índice PODE ser usado
SET enable_seqscan = off;
EXPLAIN SELECT nome FROM brinquedo ORDER BY v <=> '[1, 0, 0]' LIMIT 2;
RESET enable_seqscan;
saída esperada (trecho)
 Limit  (cost=…)
   ->  Index Scan using brinquedo_v_idx on brinquedo  (cost=…)
         Order By: (v <=> '[1,0,0]'::vector)

Faça o teste ao contrário: troque o <=> do EXPLAIN por <->. O índice deixa de ser usado, porque ele foi criado para a distância cosseno. Operador e classe de operadores precisam combinar.

7. Os vizinhos, mas só os próximos o bastante

O KNN sempre devolve LIMIT vizinhos, até para uma consulta sem relação nenhuma. Na aula, o corte pelo limiar era feito em TypeScript. No SQL, uma subconsulta resolve, e o índice continua trabalhando na consulta de dentro:

sqlpsql
SELECT nome, distancia
FROM (
  SELECT nome, v <=> '[1, 0, 0]' AS distancia
  FROM brinquedo
  ORDER BY v <=> '[1, 0, 0]'
  LIMIT 10
) AS vizinhos
WHERE distancia <= 0.5;

Saem o gato e o leão. A geladeira, a uma distância de 1, fica de fora. As duas formas (filtrar no SQL ou no TypeScript) valem na atividade.

Checkpoint. Se o seu EXPLAIN mostrou Index Scan, você já sabe a maior parte do que precisa. Saia com \q. Se quiser, apague o banco de brinquedo com docker compose -f infra/compose.yaml exec db dropdb -U biblioteca brincadeira.
04

Dicas, parte por parte

Uma ordem que funciona bem: extensão → tabela → gravar → reconciliar → buscar → fronteiras → limpar o Redis. Rode a suíte depois de cada parte. Os exemplos usam uma tabela filmes imaginária, com uma filmes_vetores ao lado: a forma é a mesma do projeto, os nomes e as decisões não.

4.1 A extensão

O prepareDatabase() (em src/composition.ts) roda quando o servidor sobe e quando a suíte de testes começa (veja tests/api.ts). Então, se o módulo Acervo criar a extensão no próprio prepare, os dois bancos (biblioteca e biblioteca_test) ficam cobertos. CREATE EXTENSION IF NOT EXISTS pode rodar quantas vezes for preciso.

A extensão é instalada por banco, não por servidor. Ter rodado no brincadeira não vale para os outros.

4.2 A tabela, e o problema da dimensão

A coluna precisa de uma dimensão fixa (vector(N)) para ganhar o índice HNSW. Só que N depende do embedder: 1024 na suíte (hash), 768 na aplicação (Gemini). E o embedder pode ser null, quando não há chave. Por isso a tabela não deve nascer no prepare, junto com as outras.

A saída é a mesma do Redis: um ensure que recebe o embedder, cria a tabela e o índice se faltarem, recria tudo se o modelo mudou e diz se precisou criar (para disparar a reconciliação). Releia ensureBookIndex no bookIndex.ts: a lógica é a mesma, mudam os comandos.

Dica: por que ${n} não funciona dentro do CREATE TABLE

A tagged template sql`…` do Bun transforma cada ${…} num parâmetro ($1, $2…). Isso protege contra SQL injection, mas o Postgres só aceita parâmetros onde vai um valor. Um tipo como vector(768) faz parte da estrutura do comando, então vector($1) dá erro de sintaxe. Para DDL com número variável, monte o texto e use sql.unsafe, mas só depois de garantir que o número é mesmo um número:

tsexemplo didático
// ❌ vira "... vector($1) ..." e o Postgres responde: syntax error at or near "$1"
await sql`CREATE TABLE filmes_vetores (v vector(${dimensoes}))`;

// ✅ "unsafe" porque o texto vai cru para o banco: valide antes
async function criarTabelaDeFilmes(dimensoes: number): Promise<void> {
  if (!Number.isInteger(dimensoes) || dimensoes < 1 || dimensoes > 2000) {
    throw new Error(`Dimensão inválida: ${dimensoes}`);
  }
  await sql.unsafe(`
    CREATE TABLE IF NOT EXISTS filmes_vetores (
      filme_id INTEGER PRIMARY KEY,
      v vector(${dimensoes}) NOT NULL
    )`);
}

Por que no máximo 2000? É o limite do índice HNSW para o tipo vector.

Dica: como lembrar qual embedder criou a tabela

Só a dimensão não basta. Dois modelos diferentes com 768 dimensões produzem vetores que não se comparam. Por isso o Redis guardava o embedder.id (modelo + dimensão), e você precisa guardá-lo também. Algumas opções, todas aceitas:

  • Uma coluna com o id do modelo em cada linha. Para saber se a tabela é de outro modelo, basta perguntar se existe alguma linha com id diferente. É a opção mais simples.
  • Uma tabelinha de metadados do módulo, com uma linha só (modelo).
  • Um comentário na tabela (COMMENT ON TABLE … IS '…'), lido com obj_description. É elegante, mas pouca gente conhece.

Se quiser conferir a dimensão da coluna que já existe, o catálogo do Postgres responde:

sqlexemplo didático
SELECT format_type(atttypid, atttypmod) AS tipo
FROM pg_attribute
WHERE attrelid = to_regclass('filmes_vetores') AND attname = 'v';
-- uma linha com tipo = 'vector(3)', ou nenhuma linha se a tabela não existe

Quando o modelo muda: DROP TABLE, criar de novo e devolver true, para quem chamou disparar a reconciliação, como o syncBookIndex já faz com o created.

Dica: a chave estrangeira

O vetor de um filme não faz sentido sem o filme. A tabela de vetores aponta para a tabela principal, e o CASCADE apaga o vetor junto:

sqlexemplo didático
filme_id INTEGER PRIMARY KEY REFERENCES filmes(id) ON DELETE CASCADE

A tabela de vetores e livros são do mesmo módulo (Acervo), então a chave estrangeira entre as duas é permitida. A regra "nada de chave estrangeira entre módulos" do schema.ts vale entre módulos diferentes. Leia também a armadilha 2 do passo 05.

4.3 Do Float32Array para o Postgres

O embedder devolve Float32Array. O pgvector aceita o formato de texto que você usou no psql, '[0.9,0.1,0]', e o ::vector converte o parâmetro:

tsexemplo didático
/** O formato de texto do pgvector: "[0.9,0.1,0]". */
function comoTextoDoPgvector(vetor: Float32Array): string {
  return `[${Array.from(vetor).join(",")}]`;
}

const consulta = comoTextoDoPgvector(new Float32Array([1, 0, 0]));
const linhas = await sql`
  SELECT nome, v <=> ${consulta}::vector AS distancia
  FROM brinquedo
  ORDER BY v <=> ${consulta}::vector
  LIMIT 2
` as { nome: string; distancia: number }[];
// linhas[0] = { nome: "gato", distancia: 0.00611… }  ← já é number

Compare com o Redis, que pedia um Buffer binário de FLOAT32 e devolvia a distância como texto.

4.4 Gravar, e só pagar o embedding quando o texto mudou

O syncIds do Redis já tem a lógica certa: monta o texto (indexText, título + autor), compara com o texto guardado e só chama o embedder para os que mudaram. Reaproveite isso. No Postgres, você pode buscar os textos guardados de todos os ids numa consulta só (com IN ${sql(ids)}, que o projeto já usa), em vez de um HGET por livro.

Para gravar, o "upsert":

tsexemplo didático
await sql`
  INSERT INTO filmes_vetores (filme_id, sinopse, v)
  VALUES (${filme.id}, ${filme.sinopse}, ${comoTextoDoPgvector(vetor)}::vector)
  ON CONFLICT (filme_id) DO UPDATE
    SET sinopse = EXCLUDED.sinopse, v = EXCLUDED.v
`;

EXCLUDED é "a linha que eu tentei inserir". Sem o ON CONFLICT, reindexar um livro que já tem vetor daria erro de chave primária duplicada.

E o contrato de "nunca lança" do syncBookIndex continua: se o Gemini cair, a escrita do livro já aconteceu e não pode virar erro 500. O livro fica sem vetor até a próxima reconciliação.

4.5 Excluir

Com ON DELETE CASCADE, o vetor some no mesmo DELETE FROM livros, na mesma transação. Pense nisto: o deleteBook ainda precisa chamar a sincronização depois do COMMIT? Não faz mal deixar a chamada lá, mas você deve saber explicar se ela ainda faz alguma coisa.

4.6 Reconciliar

O que pode estar faltando agora? Livros sem linha de vetor (o seed escreve direto em livros; o Gemini estava fora do ar quando o livro foi cadastrado) e linhas com texto desatualizado (o autor foi renomeado enquanto o Gemini estava fora). Órfãos não existem mais: a chave estrangeira não deixa.

O jeito mais simples reaproveita o que você já tem: passe todos os ids de livros para a sua função de sincronização, e a comparação de texto pula quem já está em dia. Se quiser ir direto aos que não têm vetor, um LEFT JOIN resolve:

sqlexemplo didático
-- filmes que ainda não têm vetor
SELECT f.id
FROM filmes f
LEFT JOIN filmes_vetores fv ON fv.filme_id = f.id
WHERE fv.filme_id IS NULL;

O refreshDerivedData já chama a reconciliação depois de todo seed. Se você mantiver o nome reconcileBookIndex no index.ts do Acervo, ele nem percebe a troca.

Mas olhe com atenção o src/main.ts: na subida, quem dispara o refreshDerivedData é o onconnect do Redis. Se o Redis não subir, os vetores, que agora estão no Postgres, ficam sem reconciliar. Faz sentido a reconciliação dos vetores depender do Redis? Decida onde ela deve acontecer na subida (a pergunta 3 do passo 08 volta a esse assunto).

4.7 A busca

  • A consulta do usuário vira vetor do mesmo jeito: embedder.embed([q], "query"). O "query" importa para o Gemini.
  • O KNN é o par ORDER BY coluna <=> vetor LIMIT n do passo 03, com a expressão no ORDER BY, para o índice reconhecer.
  • Se a sua função de vizinhos continuar devolvendo { id, distance }[] (o tipo KnnHit), o resto de searchBooksSemantically fica praticamente igual: o corte pelo limiar, a busca dos livros por id e o toBookView.
  • O que ainda pode dar 503? O embedder null e uma falha do Gemini. Mantenha o try/catch que transforma falha em ServiceUnavailable.
  • O teste UC24: sem embedder a busca é 503 passa { embedder: null } nas opções. Pode tirar o client das opções, mas mantenha o embedder.
  • Quando terminar, nenhum arquivo do caminho da busca semântica e da indexação deve importar infrastructure/redis.

4.8 Fronteiras

Registre a tabela nova em TABLE_OWNERS, em scripts/check-boundaries.ts, com o dono catalog. Assim, se algum outro módulo tentar ler os vetores direto, o verificador reclama. Rode bun run check-boundaries na pasta backend.

4.9 E o código do Redis?

Apague o bookIndex.ts e os dois testes dele (book-index.test.ts e knn-reply.test.ts). O Git e o roteiro da aula guardam a versão antiga. Se preferir manter as duas implementações, veja o desafio opcional. O que não vale é deixar as duas gravando ao mesmo tempo.

05

Armadilhas

Cada item abaixo já derrubou alguém. Leia antes de implementar e releia quando algo der errado.

1. Mesmo banco não quer dizer mesma transação

Agora que os vetores estão no Postgres, dá vontade de calcular o embedding dentro do inTransaction do createBook, "para ficar tudo atômico". Não faça isso. Abra src/infrastructure/transaction.ts: toda escrita pega o pg_advisory_xact_lock(22001), o que significa que todas as escritas do sistema esperam na fila. Uma chamada ao Gemini (até 10 segundos de timeout) dentro da transação seguraria a biblioteca inteira, e uma falha do Gemini desfaria o cadastro do livro. O embedding continua depois do COMMIT, onde já está.

Os testes não pegam este erro. A suíte usa o embedder de hash, que responde na hora e nunca falha. Confira a posição da chamada lendo o código.

2. Chave estrangeira sem CASCADE quebra a suíte

tests/clean-catalog.ts e src/integration/seed/seed.test.ts fazem DELETE FROM livros direto. Sem ON DELETE CASCADE, esse DELETE falha com violates foreign key constraint assim que existir um vetor, e testes que não têm nada a ver com a busca semântica ficam vermelhos.

3. A dimensão não é parâmetro

vector(${n}) dentro de sql`…` vira vector($1): syntax error at or near "$1". Veja a dica do 4.2.

4. Trocar de embedder num teste afeta todos os outros

Os testes compartilham o banco biblioteca_test. Um teste que chama a sincronização com createHashEmbedder(512), para provar que a troca de modelo refaz a tabela, apaga a tabela de 1024 dimensões que os outros testes usam. No fim desse teste, devolva o banco ao estado anterior: reconcilie com o embedder padrão e espere (await) terminar.

Pelo mesmo motivo, um embedder "quebrado" para testar falhas deve copiar o id e o dimensions do embedder padrão. Senão o seu ensure acha que o modelo mudou e recria a tabela:

tsexemplo didático
const base = createHashEmbedder();

// mesmo id e mesma dimensão, mas o embed sempre falha
const foraDoAr: Embedder = { ...base, embed: async () => { throw new Error("fora do ar"); } };

// mesmo id e mesma dimensão, mas conta quantas vezes foi chamado
let chamadas = 0;
const contador: Embedder = { ...base, embed: (textos, uso) => { chamadas++; return base.embed(textos, uso); } };

5. "O índice não está sendo usado!"

Com poucos livros, o planejador do Postgres prefere ler a tabela inteira (Seq Scan), porque é mais barato que percorrer o grafo do HNSW. Isso não é erro. Para provar que o índice pode ser usado, use o SET enable_seqscan = off do passo 03, só na sua sessão do psql. Se mesmo assim aparecer Seq Scan, confira se o operador da consulta combina com a classe de operadores do índice (<=> com vector_cosine_ops) e se o ORDER BY usa a expressão, e não outra coisa.

6. A imagem velha

Mudar o compose.yaml não troca o contêiner que já está rodando. Se aparecer extension "vector" is not available, rode docker compose -f infra/compose.yaml up -d db e confira a coluna IMAGE em docker compose -f infra/compose.yaml ps.

06

Critérios de aceite

A atividade está pronta quando todos os itens abaixo valem. Os de comportamento precisam estar cobertos por testes seus, num arquivo novo dentro de src/modules/catalog/ (por exemplo, infrastructure/book-vectors.test.ts). Use book-index.test.ts como modelo: ele cria livros pela API com testAuthor e testIsbn, e você pode ler a sua tabela com sql direto no teste.

Comportamento

  • Cadastrar um livro grava uma linha com o texto "Título — Autor" e um vetor da dimensão do embedder (vector_dims).
  • Editar o título atualiza o texto e o vetor.
  • Excluir o livro remove a linha.
  • Renomear o autor atualiza o texto dos livros dele.
  • Um livro inserido direto com SQL, como faz o seed, ganha vetor depois da reconciliação.
  • Sincronizar de novo um livro com o texto igual não chama o embedder (o embedder contador da armadilha 4).
  • Com um embedder que falha, a sincronização não lança, e o cadastro do livro não falha.
  • Um embedder de outra dimensão refaz a tabela: a coluna passa a ter a dimensão nova, e os livros voltam a ter vetor.
  • semantic-search-books.test.ts passa sem alteração nenhuma: ranking, limiar, livro excluído, 400 e 503.

Arquitetura

  • A tabela de vetores pertence ao Acervo, está em TABLE_OWNERS e tem chave estrangeira para livros com ON DELETE CASCADE.
  • O índice é HNSW com vector_cosine_ops, e a busca usa <=> com ORDER BY … LIMIT.
  • O embedding é calculado depois do COMMIT, nunca dentro do inTransaction (confira lendo o código).
  • Nenhum arquivo da indexação ou da busca semântica importa o Redis, e o Redis não guarda mais vetores de livros.
  • Nenhum arquivo fora do Acervo precisou importar arquivos internos dele. O ideal é que src/integration/ nem mude.

sqladapte aos nomes que você escolheu
-- "livros parecidos com o livro 1", direto no banco
SELECT l.titulo, round((v.coluna_do_vetor <=> alvo.coluna_do_vetor)::numeric, 3) AS distancia
FROM sua_tabela v
JOIN livros l ON l.id = v.livro_id
CROSS JOIN (SELECT coluna_do_vetor FROM sua_tabela WHERE livro_id = 1) AS alvo
ORDER BY v.coluna_do_vetor <=> alvo.coluna_do_vetor
LIMIT 5;

Desafio opcional: as duas implementações atrás de uma porta

Não vale ponto extra, mas é o melhor treino de portas e adaptadores do semestre. Em vez de apagar o Redis, crie uma porta, por exemplo BookVectorStore, com as operações que a busca e a indexação usam (algo como sincronizar ids, reconciliar e achar os vizinhos de um vetor), e dois adaptadores: o do Redis (o bookIndex.ts de hoje, quase sem mudança) e o seu, do pgvector. Uma variável de ambiente, como VECTOR_STORE=pgvector|redis, escolhe qual usar, como EMBEDDING_PROVIDER escolhe o embedder em embedder.ts.

O teste que mostra que deu certo: a mesma bateria de testes rodando contra os dois adaptadores, com o mesmo resultado. Se você conseguir, responda também: o que precisou entrar na porta que você não esperava?
